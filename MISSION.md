# Zartema engineering mission

Zartema is an authorized JVM bytecode transformation and legitimate software-protection engine, maintained as `estacyl`. Its implementation baseline is Java 21. It excludes security-tool evasion, malicious concealment, anti-analysis mechanisms, and unauthorized bypass of third-party protections.

This document preserves the original mission and its OBA V3 continuation. A milestone, passing build, or published commit is not completion. Work continues across context changes until every acceptance criterion below has concrete evidence, or an actual blocker, enforced resource limit, or user interruption prevents further work.

## Requirements

- **M01 — Knowledge and evidence:** Use OBA V3's workflow, task routing, direct technical references, integration and artifact contracts, and evidence protocol. Select applicable skills by domain, read relevant sections before consequential decisions, verify version-sensitive claims against specifications, pinned APIs or experiments, and record actual reads and outcomes. Do not copy the OBA knowledge base into this repository.
- **M02 — Architecture:** Maintain a coherent, extensible system with explicit API, component boundaries, state ownership, class-file authority, analysis scope and snapshot identities, lifecycle, invalidation, failure behavior, configuration, diagnostics, and ADRs. Avoid unnecessary conversions, speculative abstractions and silent fallbacks.
- **M03 — Mandatory libraries:** OW2 ASM owns class-file reading, editing, metadata, emission and applicable structural checking; IBM WALA provides independently justified program analysis; SootUp provides higher-level IR/CFG/data-flow or call-graph capabilities where appropriate. Each must influence an actual engineering decision, check, or supported workflow. Snapshot, dependency, runtime-view, and uncertainty contracts are explicit. Agreement is not proof.
- **M04 — Artifacts and runtime:** Implement bounded JAR ingestion and deterministic emission; preserve or explicitly reject unsupported entries and metadata, enforce signature policy, and support physical and effective multi-release JAR views across declared target releases. Provide dependency and hierarchy resolution, respecting class loader, module, linking, initialization, dynamic linkage, and runtime compatibility limits.
- **M05 — Transformations and compatibility:** Implement configurable transformation lifecycle and explicit per-pass supported input domain, preconditions, postconditions, observable behavior, structural invariants, failure policy and limitations. Provide conservative identifier renaming and functional keep rules. Preserve or explicitly exclude reflection, JNI, serialization, resources, external configuration, instrumentation and other name-sensitive contracts.
- **M06 — Operator interfaces:** Provide an extensible public API and CLI, validated configuration, mapping generation and stack-trace translation, diagnostics, machine-readable execution reports, and accurate per-element apply/skip/failure information. Every documented option and component must have an actual consumer and test.
- **M07 — Verification and tests:** Separate class-file structural checks, actual target-JVM verification and loading, and bounded behavioral equivalence. Cover unit, integration, end-to-end, differential, property-based, regression, malformed-input, compatibility, reproducibility and performance cases, including licensed real-world fixtures where appropriate. Do not fabricate results or suppress failures. Record exact inputs, JVM/tool versions, observations and untested cases; finite tests do not prove universal equivalence.
- **M08 — Build and operations:** Pin compatible dependency versions, support reproducible clean-checkout builds, maintain Java CI and inspect actual results, measure performance before optimization, and complete an independent final audit plus defect correction.
- **M09 — Licensing and identity:** Retain Apache-2.0 unless a documented review justifies a change. Review actual direct and transitive licenses and distribution obligations; preserve third-party notices. Use `estacyl` consistently in project-owned metadata, English for all new project content, and avoid exposing credentials, personal information, local caches or unrelated files.
- **M10 — Continuity and publication:** Maintain `AGENTS.md`, `PROJECT_STATE.md`, ADRs and engineering evidence. Commit coherent, validated milestones, inspect every public push for secrets and unrelated material, and publish through the authorized repository at https://github.com/Estacyl/zartema without destructive Git operations or stable releases unsupported by evidence.

## Definition of done

Completion requires all M01–M10: a reproducible clean-checkout build; meaningful operational ASM/WALA/SootUp integration; an end-to-end transformation workflow with effective keep rules and configuration; valid emitted artifacts and actual runtime/differential evidence within a declared domain; passing compatibility/regression tests; measured performance and reproducibility; reviewed dependency licenses and accurate documentation; a completed independent engineering audit with critical defects corrected; validated commits published and actual CI results inspected. Missing, weak, contradictory or indirect evidence does not satisfy a requirement.
